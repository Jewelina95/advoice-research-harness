# ADvoice v2：理论、实验设计与架构

日期：2026-10-08。状态：设计稿，未实现、未跑真实数据。本文基于仓库文档、历史审计数字和 SpeechCARE 论文（npj Digit. Med. 2025，PMC12623413），不新增实验结论。

## 0. 目标与实验

用途：AD 早期筛查辅助。一段患者语音输入，输出 HC / MCI / AD 的筛查估计，并用具体的 metric 和 state 说明依据，帮助医生完成初筛。

核心实验是三个条件的比较：

| 条件 | 内容 |
| --- | --- |
| A | 传统声学基线：手工声学特征 + 分类器 |
| B | 纯 Agent：同一个 LLM 直接读病例（转录/音频描述），没有本框架 |
| C | 本框架 + Agent：SSL 表示、MetricEvidence、StateCard、知识库与约束、监督训练、Agent，联合训练与校准 |

要证明的是 C 优于 A、C 优于 B，并且 C 的判断依据（metric/state）可信。数据按受试者分组，80% 训练（内部再做嵌套交叉验证）、20% 测试且只看一次。

## 1. 训练到底学的是什么

### 1.1 SpeechCARE 学的是什么

- mHuBERT（声学，约 98M 参数）与 mGTE（文本，约 305M 参数）随任务训练调整，加一个可学习的 [CLS]。
- Adaptive Gating Fusion：受 mixture-of-experts 启发的门控网络，对每个样本动态给声学、语言、人口学三路分配权重。论文报告的“各任务平均门控权重”就是你说的“权重和比例”。
- 分类头。
- LLM（LLaMA-3.1-70B）只在离线预处理中用来识别只有临床医生说话的转录和标注任务类型，不参与判断；没有 Agent。
- PREPARE：1,646 训练 / 412 测试，10 个随机种子，F1 72.11%，micro AUC 86.83%；单个检查点上 MCI 召回 43%（阈值优化后 55%）。

所以 SpeechCARE 学的是“表示 + 每个样本的模态比例 + 分类边界”，其中门控比例是唯一的可解释输出，粒度只到“声学 vs 语言”。

### 1.2 我们当前学的是什么（代码事实）

| 层 | 学什么 | 怎么学 | 现状 |
| --- | --- | --- | --- |
| SSL 编码器 | 不学 | mHuBERT-147、gte-multilingual 冻结 | 只取最后一层；音频只看前 30 s |
| Metric | 不学数值本身；学“正常是多少” | 训练折内健康参考的中位数/尺度 → 方向化 z 分数 | 已实现 |
| State 内部权重 | 不学 | `configs/states/audio_states.yaml` 手工写死（如 S01 = 0.30/0.30/0.20/0.20） | 这是知识先验，不是学出来的 |
| 各分支专家 | 学 | 声学指标、文本指标、状态、mHuBERT、文本 embedding 各一个 L2 逻辑回归，折内拟合 | 已实现 |
| 分支间比例 | 学 | 静态多项逻辑 stacking（所有病例同一组比例）；另有一个与 SpeechCARE 类似的动态可靠度门控（48 维 MLP，输入为各专家概率和可靠度），但在嵌套选择中未胜出 | 已实现 |
| 两头分类 | 学 | HC vs 受损；MCI vs AD | 已实现 |
| 校准 | 学 | OOF 校准器 | 已实现 |
| Agent 权重 | 学 | 融合系数 [base, agent, replay]，先验向 0 收缩 | 历史上学到 ≈ 0 |
| Agent 本身 | 不学 | 知识库 + prompt + 工具，推理时使用 | — |

结论：我们也在学“权重和比例”，而且有与 SpeechCARE 同类的动态门控。区别有三点：编码器没有微调；state 内部权重是手工知识先验；门控的输入是可靠度而不是任务与证据可观察性。

## 2. 理论：为什么 C 应该优于 A 和 B

用一个标准分解来讨论：一个分类器的错误 = 输入信息不够导致的不可约错误 + 从有限标签学映射带来的估计误差 + 分布变化（换数据集/设备/语言）带来的错误。

### 2.1 A 的位置

A 只看声学。信息不够：语义、内容、任务完成这类认知语言学信号在声学里只有间接体现。参数少、估计误差小。容易学到设备、录音条件的捷径，跨数据集退化。

### 2.2 B 的位置

B 的优势：LLM 能读懂语义，自带医学常识，不需要标签，没有估计误差。

B 的三个结构性缺陷：

1. 没有人群校准。LLM 不知道这个数据集的类别基线，也不知道“普通话图片描述的正常停顿率是多少”，只能凭常识猜，输出的是偏好不是概率。
2. 感知不到声学时间信息，除非有人先把它测出来。
3. 没有从标签学到任何映射。我们的历史数据里，通用 LLM 读状态得到的判别力接近随机（AUROC 0.48–0.53）。

### 2.3 C 能优于 A 和 B 的四个理论依据

**依据 1：堆叠的下界（最硬的一条）。** 如果 C 把 A 型特征、B 型 Agent 判断都作为候选输入，在嵌套交叉验证下做堆叠，那么由 Super Learner 的 oracle 性质，C 在样本足够时至少和其中最好的那个一样好。要超过它们，需要各部分的错误不完全重合。这条给出的是“C 不劣于 max(A, B)”的设计保证，前提是 B 的输出确实作为一个候选进入 C。当前 C 的 Agent 用的是框架包，不是 B 的原始判断，严格讲这条保证还没建立；改法见 §3.3。

**依据 2：知识结构降低估计误差。** 每个数据集只有几十到一千多例。把几十个相关指标先按临床构念聚成十几个状态，再训练分类器，等于用领域知识做降维，参数更少，小样本下方差更低。手工的 state 内部权重就是这里的强先验：小数据集上它应该比自由学习更稳，大数据集上可以放开学习。这是 C 相对“把所有特征直接扔给分类器”的理论优势，也是相对 SpeechCARE 的优势所在：SpeechCARE 的门控只有三路，我们的门控对象可以是十几个有临床含义的状态。

**依据 3：治理约束降低分布变化下的错误。** QC/设备变量不得作为疾病证据；任务不可观察的状态不算作正常（缺失中性）；健康参考按任务和语言分开。这些约束切断的正是 A 和 SpeechCARE 都可能学到的捷径。理论上它不保证提高同分布测试的准确率（框架命题 5），可检验的预测是：留一数据集外验证时，C 的退化比 A 小。

**依据 4：框架把 Agent 的任务从“判断”变成“测量”。** B 的 LLM 要同时完成“理解语义、知道正常范围、映射到类别”三件事，后两件它做不好。C 让监督模型负责正常范围和类别映射（有标签的部分），只让 Agent 做它独有能力的部分：读懂内容，按知识库里的评分键测量内容单元、连贯性、回忆遗漏与侵入、任务完成度。理论上，这正是 C 中 Agent 能提供 A 和监督模型都没有的信息的地方，也是依据 1 里“错误不完全重合”的来源。

### 2.4 现在为什么还没成立

| 依据 | 现状 | 缺口 |
| --- | --- | --- |
| 1 堆叠下界 | Agent 以融合系数形式进入，先验收缩、样本小 | B 的原始判断没有作为候选；评估集 16–30 例测不出 |
| 2 知识降维 | 状态主要是停顿/发声/韵律 | 认知语言学状态（S09、S10、S11、S14）大多未启用 |
| 3 治理约束 | 已实现 | 没有做过留一数据集外的对照，优势没被测量 |
| 4 Agent 测量 | Agent 读的是监督模型已经用过的同一批状态 | Agent 没有提供新信息，所以增益 ≈ 0（178/412 改概率，2 例改类别，1 对 1 错） |

另一个与目标直接冲突的问题：预测与解释来源不一致。医生端 demo 病例 05（`MCI_F_122608`）判 MCI 81.7%，但三条主要表现两条“接近健康参考”。概率主要来自 embedding 分支，报告只能讲状态。目标要求“分类由对应的 metric 和 state 指出”，当前结构做不到这一点（见 §3.1）。

## 3. 设计改进

### 3.1 可分解预测：让依据真的是依据

```
logit_k(x) = Σ_s β_{k,s}(g) · z_s(x)     # 状态贡献，可解释
           + γ_k · r_k(x)                  # SSL embedding 残差，不可解释
           + b_k
```

- `z_s`：训练折内健康参考下的方向化状态分，不可观察时为 0。
- `β(g)`：状态权重，可以随任务/可观察性 g 变化（见 3.2）；这就是我们版本的“学习权重和比例”，粒度是状态而不是模态。
- `r_k`：embedding 分支对状态未解释部分的拟合。
- 报告按 `β·z` 排序“支持这一结论的主要表现”，并给出可解释占比；残差主导时报告必须如实写“可解释依据不足”。
- 用 OOF 比较两件事：残差带来的 AUROC 增量，和可解释占比。两者都报告。

### 3.2 证据条件门控：吸收 SpeechCARE 的优点

把 SpeechCARE 的样本级门控搬进来，但门控的输入换成治理变量：任务类型、各状态是否可观察、各状态可靠度。门控输出的是对各状态（及残差分支）的样本级权重。

相对 SpeechCARE 的理论优势：它的门控输入是隐藏表示，权重只能解释到“声学 vs 语言”；我们的门控输入本身就有临床含义，权重解释到“这个病例因为是图片描述任务、录音质量差，所以更依赖内容单元而不是停顿”。小样本下门控必须低容量（例如逻辑型门控），否则会重演历史上动态门控在嵌套选择中落选的结果。

### 3.3 Agent 的三个角色

| 角色 | 产出 | 进入哪里 |
| --- | --- | --- |
| 测量仪器（主） | 新 MetricEvidence：内容单元、语义连贯/偏题、回忆遗漏与侵入、流畅性聚类与转换、句法复杂度，均引用片段 | 状态层，与其他状态一起被学习权重 |
| 独立判断（满足依据 1） | 与 B 同样的类别判断，但在框架约束下给出 | 堆叠的一个候选输入；学不到增益时系数为 0 |
| 质量审计 + 报告 | ASR/角色问题 → 可靠度下降或证据撤销；按锁定的贡献表写报告 | 可靠度与报告，不改数字 |

知识库在其中的作用要具体化：不是泛泛的“AD 知识”，而是每个任务的评分键（如图片的信息单元表、故事回忆的要点表）、状态定义与方向、不可做的推断清单。Agent 的测量质量直接取决于评分键质量。

### 3.4 实验设计：把“C 为什么好”拆开测

只比 A、B、C 三个数，赢了也说不清赢在哪。建议在同一 80/20 划分、同一测试集上跑一组嵌套对照：

| 臂 | 组成 | 回答的问题 |
| --- | --- | --- |
| A | 手工声学 + 分类器 | 传统基线 |
| A+ | A + 文本指标 + SSL embedding（不含状态和 Agent） | 只靠更多特征能到哪 |
| S | A+ + MetricEvidence/StateCard/治理约束（无 Agent） | 框架本身的价值（依据 2、3） |
| B | 纯 Agent，无框架 | 通用 LLM 能做到哪 |
| B′ | 同一 LLM + 框架输入（知识库、状态、评分键），不接监督模型 | 框架让 Agent 本身变好多少（依据 4） |
| C | S + Agent 测量 + Agent 判断堆叠 + 校准 | 完整系统 |

主要对比：C vs A、C vs B（论文主结论）；S vs A+（框架贡献）；C vs S（Agent 贡献）；B′ vs B（框架对 Agent 的贡献）。

统计设计：

- 主终点预注册一个（建议 Macro AUROC，次要为 log loss、MCI 召回、校准）。
- 模型选择、阈值、λ 只在训练集的嵌套交叉验证里做；20% 测试集只评估一次。
- Agent 贡献的主分析放在训练集完整 OOF 上（样本量大得多），测试集用于确认。
- 多数据集只训练不混库，效应量按数据集分层合并（配对 bootstrap），同时报告每个数据集的方向。
- 留一数据集外验证作为依据 3 的检验。
- GPT / Claude / DeepSeek 在 B、B′、C 三个臂中替换，其余全部固定，这样“模型越强、框架收益越大”可以被直接检验。

### 3.5 预期和风险

- C > A：可能性高。历史上同编码器下加入认知框架已有 Accuracy +0.075、Macro AUROC +0.060。
- C > B：可能性高。B 没有校准，三分类尤其 MCI 难。
- C > S（Agent 净增益）：这是真正的研究风险，历史为 0。成立的前提是 3.3 的 Agent 测量带来新信息；如果内容单元等测量与监督模型已有的文本 embedding 高度重合，增益仍可能很小。
- 与 SpeechCARE 的绝对差距（Accuracy 0.672 vs 0.721）主要来自编码器未微调，这与 Agent 无关，需要单独处理（PREPARE 规模下折内轻量微调）。

## 附录 B. 工程整合方案

目标是一条主线、一个单例入口、一份可观察性定义。

1. **单例入口** `advoice screen <audio> --task <task> --bundle <model_bundle>`：解码 → ASR → 测量 →（可选）Agent 测量/审计 → 状态 → 加载冻结模型包预测 → 锁定 → 报告。模型包由训练命令导出，包含状态参考、β、残差分支、校准器和全部哈希。demo 改为调用它。
2. **主线收敛**：`pilot/` 的 contracts/learning/runtime/reporting 作为唯一主线。B2/B3/report/scoring 四个旧 Agent、`authority_*`、`conditional_authority*` 在 pilot 复现历史 B/J 数字后移入 `advoice/legacy/`，只保留复现历史报告所需的入口。`report_agent.py` 现在即可删除（仅测试引用）。
3. **一份可观察性**：`configs/observability/default.yaml` 的 `task_state_matrix` 与各 channel yaml 的 `enabled_states` 合并为单一来源，代码只读这一份。
4. **一个 provider 层**：pilot 的 `AssessmentProvider` 协议用 `agent_runtime.run_api_batch` 实现真实适配器（已支持 OpenAI/Claude/DeepSeek）；所有外发统一经过 pilot 去标识与注入隔离，B2 的未去标识外发路径关闭。
5. **配置与代码默认值一致**：门槛、模型 ID、窗口长度只从配置读。

## 附录 C. 落地顺序

1. 单例入口 + 模型包导出（不改模型，先让现有 Condition C 能对一个新 MP3 出概率）。
2. 可分解预测：在现有分支专家上改为“状态线性头 + embedding 残差头”，报告显示贡献表和残差占比。用 PREPARE 开发集 OOF 比较与现有主干的 AUROC 差。
