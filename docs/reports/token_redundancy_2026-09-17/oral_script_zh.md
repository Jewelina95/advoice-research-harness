# ADvoice Agent 调用冗余优化：中文口语汇报

这次我们没有调整预测模型，也没有重新跑患者数据。我们解决的是 Agent 调用链里的工程冗余：为什么同样一个病例会发送过多内容，为什么历史调用很难解释 token 消耗，以及怎样在不删除医学证据的情况下把调用协议压缩下来。

原来的消耗主要来自五个位置。第一，MetricEvidence 使用很长的完整 ID，其中反复包含数据集、病例、任务、指标和状态信息。第二，输出 Schema 按照“状态乘以动作”的方式展开，同一组证据 ID 会为 downweight、invalidate、mark unavailable 和 retain 重复三到四遍。第三，盲评和协调两个阶段都会加载完整规则包，其中混入了当前决策不需要的报告写作合同和参考文献。第四，应用层五次重试叠加 SDK 默认重试，极端情况下一个逻辑请求可能产生十五次传输。第五，旧程序只保存最终 JSON，没有保存真实的输入、输出、缓存和推理 token，因此历史费用无法精确追溯。

这次最重要的修改，是把证据的“传输身份”和“审计身份”分开。系统内部仍然保存完整的 MetricEvidence ID，用于追溯数据集、任务、指标、状态和片段；模型只接收 E001、E002 这样的病例内短 ID。模型返回结果后，系统先把短 ID 恢复成完整 ID，再进行未知证据检查、跨状态引用检查和动作合法性检查。因此，压缩发生在传输层，没有损失证据链。

第二个修改是重写输出 Schema。以前同一个状态下的证据列表会针对每一种动作重复一遍；现在每个状态只声明一次允许引用的证据，动作和倍率是否合法由本地类型系统校验。例如，downweight 只能使用零点二五、零点五或者零点七五；invalidate 和 mark unavailable 必须为零；retain 必须为一。也就是说，我们缩短了 Schema，但没有把约束交给大模型自由判断。

压缩结果是可测量的。我们用七十一份历史 Schema 做了等价重建。它们的总大小从大约二点零二 MB 降到零点三四 MB，减少了百分之八十三点二。最大的 PROCESS-2 advisor Schema 从八万两千零四十七字节降到五千七百四十五字节，减少百分之九十三。这里需要明确：这是 Schema 字节的变化，不等于账单 token 一定下降同样的比例，因为真实费用还取决于患者转录长度、医学规则长度、模型推理 token、缓存和失败重试。

第三个修改是调用治理。SDK 内部重试已经关闭，应用层最多进行三次传输尝试，不再出现五乘三的嵌套重试。单次结构化输出上限从一万两千 token 调整到四千零九十六 token。每次调用都会产生独立的 usage 账本，记录模型、尝试次数、耗时、输入 token、输出 token、缓存 token 和推理 token。账本不保存患者转录、prompt 内容或 API 密钥。

医学规则没有被整体删除。当前决策阶段仍然保留医学范围、AD 认知状态知识、任务可观察性、混杂因素、证据层级、认知回退协议、报告权限和标签泄漏规则。只把参考文献列表和报告写作合同移出决策调用。医生报告功能仍然保留，但在当前框架测试和 demo 中不运行；正式流程中，报告必须在预测结果和证据链锁定之后单独生成，不能反过来修改诊断结果。

还有一部分重复必须保留。系统采用两阶段判断：第一阶段让 Agent 在看不到监督概率的情况下独立审查证据；第二阶段才展示监督模型的统计结果，让 Agent 处理冲突并提出有引用依据的状态修正。因为两次调用是无会话状态的独立请求，两次都需要核心医学边界。删除这部分会重新造成概率锚定，影响我们验证 Agent 是否真正提供了独立信息。

工程验证方面，目前全量测试为七百七十项通过，三项跳过。测试覆盖短 ID 双向还原、证据引用、跨状态拒绝、倍率规则、缓存复用、token 账本以及原有融合逻辑。本轮没有重新训练，也没有跑新的患者推理，所以它证明的是调用协议更紧凑、审计更完整，不代表准确率已经提升，也不代表已经超过 SpeechCARE。

下一步不需要直接跑全量数据。应该先选择固定的小型验证集，用同一模型和同一病例分别运行旧协议与新协议，比较每例的真实 input、output、cached 和 reasoning token，同时确认两边产生的结构化决策完全一致。只有完成这个一致性检查后，才适合把紧凑协议用于正式权重校准和跨数据集评估。
